# Specra frontend (apps/web)

Next.js 16 (App Router) · React 19 · Tailwind 4 · shadcn/ui · next-intl · TypeScript strict.

## Layout

Organised by feature. A feature owns its queries, components and schemas; `components/`
holds only what more than one feature uses.

```text
src/
├── app/[locale]/       layouts and thin pages, in (marketing) · (auth) · (app) groups
├── i18n/               routing · navigation · request config · bundle parity test
├── messages/           en.json · vi.json — every user-facing string
├── features/           notes · chat · auth · settings · dashboard
├── components/         ui/ (shadcn) · layout/ · common/ · theme/ · i18n/
├── lib/                api/ · config/ · utils
└── proxy.ts            locale routing at the edge
```

A `page.tsx` resolves params, calls `setRequestLocale`, and renders a view from
`features/`. Logic in a page cannot be tested without a router.

Adding or changing a page or a feature? Read `specra-feature` first — it is the end-to-end
checklist, and it points back here for the Next/TanStack/shadcn detail. Which folder a file
belongs in, and what may import what, is `specra-architecture`.

`apps/web/AGENTS.md` (written by Next.js) warns that Next 16 carries breaking changes.
The correct documentation ships inside `node_modules/next/dist/docs/` — read it there
rather than writing from memory.

## Version traps — this is not the release you know

### TanStack Table is **v9**, not v8

There is no `useReactTable`, no `getCoreRowModel()`, no old-style `columnHelper`. The
current API:

```tsx
// Declared outside the component, as TanStack requires
const features = tableFeatures({
  rowSortingFeature,
  sortedRowModel: createSortedRowModel(),
  sortFns: { text: sortFn_text, datetime: sortFn_datetime },
});
const helper = createColumnHelper<typeof features, Note>();

// helper.columns([...]) is REQUIRED — a bare array widens the types and fails to compile
const columns = useMemo(() => helper.columns([ helper.accessor(...), ... ]), [deps]);

const table = useTable({ features, columns, data, state: { sorting }, onSortingChange });
```

- `onSortingChange` must be `OnChangeFn<SortingState>` (it receives an updater), not
  `(s: SortingState) => void`. A `useState` setter matches that signature directly.
- Render through `<table.FlexRender header={header} />` / `cell={cell}`.
- The v8 API still exists at `@tanstack/react-table/legacy` — do not use it for new code.

Full reference implementation: `src/features/notes/components/notes-table.tsx`.

### Next 16: `params` and `searchParams` are Promises

```tsx
export default async function Page({ params }: PageProps<"/[locale]/notes/[id]">) {
  const { locale, id } = await params;
  setRequestLocale(locale);
  return <NoteDetailView noteId={id} />;
}
```

Every route sits under `[locale]`, so the generated type paths start with `/[locale]/…`.
Route groups — `(app)`, `(auth)`, `(marketing)` — do not appear in them.

`PageProps` / `LayoutProps` are generated by `next typegen`. If you add a route and TS
reports `does not satisfy the constraint '"/"'`, run:

```bash
pnpm typecheck    # already includes next typegen
```

### Zod 4 with TanStack Form

Zod 4 implements Standard Schema, so TanStack Form consumes it directly:

```tsx
useForm({ defaultValues, validators: { onSubmit: noteSchema }, onSubmit });
```

## Server state vs client state

This boundary is deliberate — do not blur it:

- **TanStack Query** holds everything that belongs to the server. The hooks live in each
  feature: `src/features/notes/api/`, `src/features/chat/api/`.
- **Zustand** (`src/stores/ui-store.ts`) holds UI preferences only. `persist` saves just
  `streaming` and `ragMode`; the conversation id is deliberately not persisted.

Never copy server data into Zustand and sync the two.

## Calling the API

**`specra-web-api` is the skill for this** — read it before writing a query, a mutation, or
anything in a feature's `api/` folder. The short version:

- Every request goes through the **axios** instance in `src/lib/api/client.ts`, called through
  the `http.get` / `post` / `put` / `patch` / `delete` helpers, which already unwrap
  `response.data`. Never `fetch`, never a bare `axios`, from a feature.
- Interceptors add `Authorization`, `Accept-Language` and `X-Request-Id`, turn every failure
  into `ApiError`, and refresh the access token once on an `invalid-token` 401.
- `queryFn: ({ signal }) => http.get(url, { signal })`; query strings are `params`, not string
  concatenation; keys come from the feature's key factory. `retry` is already configured in
  `providers.tsx` to skip 4xx.
- Branch on `error.code`, never on the message — it is translated per request. `status === 0`
  means the API could not be reached at all, not an HTTP error.
- The SSE stream in `features/chat/api/ai.ts` is the one thing still on `fetch`, and it takes
  its headers from `streamHeaders()`.

```tsx
serverErrors={mutation.error instanceof ApiError ? mutation.error.fieldErrors : undefined}
```

`src/lib/api/types.ts` holds the **hand-written** types the code actually uses.
`src/types/api.d.ts` is generated (`pnpm gen:api`, needs the API running) and exists only for
cross-checking — springdoc marks every field optional because Java records emit no `required`,
so the generated version is looser. Do not import from the generated file.

## Internationalisation

Never write a user-facing string in a component. Add it to `src/messages/en.json` **and**
`src/messages/vi.json`, then read it:

```tsx
const t = useTranslations("notes"); // client
const t = await getTranslations("notes"); // server
const t = await getTranslations({ locale, namespace: "notes" }); // generateMetadata
```

`src/global.d.ts` types every key against `en.json`, so a typo is a compile error rather
than a key rendered on screen. `src/i18n/messages.test.ts` then checks that every bundle
has the same keys _and_ the same ICU placeholders.

Rules that are easy to get wrong:

- **Import `Link`, `useRouter`, `usePathname` from `@/i18n/navigation`**, never from
  `next/link` / `next/navigation`. Those add and strip the `/vi` · `/en` prefix; the Next
  versions do not, and would drop the user out of their language. `useParams` and
  `useSearchParams` still come from `next/navigation`.
- **Every layout and page calls `setRequestLocale(locale)`** before reading a translation,
  or the segment silently opts out of static rendering.
- **Build Zod schemas from a translator**, in a `useMemo` — a module-level `z.object`
  captures whichever language loaded first (see `features/notes/schemas.ts`).
- **Format dates with `useFormatter`, and only in a client component.** Never
  `toLocaleString()`. The API sends every instant as ISO-8601 UTC and `i18n/request.ts`
  pins no `timeZone`, so a timestamp renders in the reader's own timezone — which is the
  point. That only holds on the client: formatting a date in a **server** component renders
  it in the server's timezone and then hydrates into the reader's, which is a mismatch.
  Pass the raw ISO string down to a client component and format it there.
- **A relative time needs a `now`: `format.relativeTime(date, useNow())`.** Without one,
  next-intl falls back to `Date.now()` per call — a different instant on the server than in
  the browser — and logs `ENVIRONMENT_FALLBACK`. Do **not** fix this by putting `now` in
  `i18n/request.ts`: that config is shared with statically rendered segments, so the instant
  freezes at build time and "2 hours ago" drifts forever. `useNow({ updateInterval: 60_000 })`
  keeps it ticking in the one place that has a real clock.
- Switching locale means `router.replace({ pathname, params }, { locale })`, so the user
  stays on the page they were on.

Adding a language: a constant in `src/i18n/routing.ts`, a label in `LOCALE_LABELS`, a
bundle in `src/messages/`, the matcher in `proxy.ts`, and the matching
`messages_xx.properties` on the API.

## shadcn/ui

Configured in `components.json`: base `radix`, style `radix-nova`, icon library `lucide`,
stylesheet `src/styles/globals.css`.

```bash
pnpm dlx shadcn@latest add <component>
```

Components land in `src/components/ui/` — edit them freely, they are project code.

Two traps in this preset:

- `CommandDialog` here does **not** wrap its children in `<Command>`, unlike the plain
  shadcn variant. Without that wrapper every `CommandInput`/`CommandItem` reads an
  undefined cmdk store and the page throws on render.
- Generated components arrive unformatted and sometimes with an effect-plus-setState
  hook that fails lint (`use-mobile.ts` was rewritten with `useSyncExternalStore`). Run
  `pnpm format && pnpm lint` right after adding one.

Fonts: the locale layout binds `--font-sans` to Geist. The shadcn preset declares
`--font-sans: var(--font-sans)`, so without that binding the font resolves to nothing.

## Theming

next-themes with `attribute="class"`, three choices: light, dark, system. Both the header
dropdown and the settings page write through `useTheme`.

Do not add a "mounted" guard to avoid a hydration mismatch — see the lint rule below.
Render both states and let a CSS `dark:` variant pick, as `theme-toggle.tsx` does.

## Linting

ESLint 9 flat config, including React 19's `react-hooks` rules. Frequent failures:

- `react-hooks/set-state-in-effect` — an **error**, not a warning. The familiar
  `useEffect(() => setMounted(true), [])` hydration guard and
  `useEffect(() => setPage(0), [query])` reset are both rejected. Fix by deriving the
  value, setting it in the event handler that caused it, or subscribing with
  `useSyncExternalStore`.
- A bound `catch` variable that goes unused → use `catch {}` or pass it on as `cause`.

## Tests

```bash
pnpm test         # Vitest, jsdom — in apps/web
pnpm test:e2e     # Playwright — from the repo root; lives in tests/e2e, not here
```

Playwright is **not** a dependency of this app. The suite is its own workspace package
(`specra-e2e`) so it can be pointed at any deployment with `E2E_BASE_URL`; with that unset
it builds this app and serves it on :3100 itself.

The Vitest config is `vitest.config.mts` (the `.mts` extension is what makes Vite load
it as ESM).

E2E runs whether or not the API is up, so it only asserts on things the UI must get right
in either case — routing, locale, theme, the command palette, client-side validation. Do
not write e2e tests that depend on backend data.

Expected text is imported from `@messages/*.json` rather than written out in the spec:
a copy of a string in a test is a second translation nobody remembers to update.

Two things to know:

- The suite runs against a **production build on port 3100**, not `next dev`. Eight parallel
  workers hitting a cold dev server race each other over Turbopack manifests, and the run
  fails with `JSON.parse` errors from inside Next that say nothing about the app. The
  separate port also means a developer's own `pnpm dev` can keep running.
- `/` redirects by `Accept-Language`, so a root-redirect assertion has to pin the locale
  with `test.use({ locale: "vi-VN" })`.
